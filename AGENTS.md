# HPG Mission Companion repository contract

## Mandatory start gate

1. Run `node tools/assert-main-branch.js`; work only on `main`, with hooksPath `.githooks`. There is a single branch: no integration branch, no PR merge step.
2. Exactly one registered Git worktree may exist: this folder. Any second worktree, clone, parallel checkout or alternate copy of the sources is a blocking violation. The runtime folder of the app (for example `Desktop\HPGMissionCompanion`) holds only built outputs and user data, never sources.
3. Read `docs/WORKSPACE_MAP.md`. Inspect `git status --short`, preserve user changes and name the semantic scope before editing.

## Source and safety

- Edit `src/`; never edit a built executable. `tools/build.cmd` is the only way to produce `HPGMissionCompanion.exe`.
- Never commit binaries or user data: executables, dlls, wav, onnx, zips, `piper/`, `voices/`, `backups/`, `audio/`, `HPGMissionCompanion.json`, logs. `tools/check.js` fails on them. The Piper engine and the voices are downloaded by the user from their own sources and are never redistributed here (`THIRD_PARTY.md`).
- User-facing strings and source files are ASCII-only unless explicitly requested.
- The repository is under a custom licence (`LICENSE`): use is free for everyone; modification, copying, redistribution, derivative works and sale need the author's explicit written consent. Never add an open-source licence, copy in code or assets whose licence does not allow it, or change the licence without the user's explicit decision.
- The text tags and the WebSocket protocol are a contract with the HPG missions (`docs/architecture/TAGS_AND_PROTOCOL.md`): keep them backwards compatible and change the document, the tests and the changelog in the same change.
- Destructive or external actions of the app stay behind the user: cleaning the HPG work folder always shows the groups, asks for confirmation (with a warning for the configuration and settings groups) and backs up first by default; only the first group (debug) is ticked for the user, `global.json` has its own unticked group; the `EXE.xml` of the simulators is edited only by the app's own code, keeping the `.bak` copy; downloads happen only on a user click, from the documented sources, with md5 checks where the source gives them. Test every destructive path on a dummy copy, never on the user's real folders.
- A published release always carries notes in its body (the update question and the What's new button show them): the mission release body is the user changelog extract of the builds since the previous release, the program release body is its changelog; never publish a release without them.
- The mission update writes only `hpgmission\RANDOM AND EVERYWHERE\everywhere_all.json` of a package and keeps the backup beside it as `.json.bak`; the test copies of the user beside it are never replaced by themselves. Copy mission files with a stream copy, never File.Copy (the Community folder is EFS-encrypted).
- Check for updates (the button of the window footer, which opens the Updates tab; the user's request of 2026-10-11) runs at the start of the program (option on by default, at every start, no time limit, GitHub only: the 6 hours of the first version were for the Google Drive link and the user dropped them on 2026-10-13) and on the user's click; the automatic run only reads and tells, and nothing is downloaded or replaced without the question; the mission is replaced before the program, the old mission file is copied outside the Community folder first, and the setup is started with the folder of the running program; the Updates tab lets the user install both, only the mission or only the program (setting `UpdateWhat`) and shows the news in amber; never add a periodic check while the program runs, or an automatic install, without the user's request.
- The mission index update runs on the user's click, and at start only while the option "Update the index automatically when the app starts" is ticked (on by default, the user's request of 2026-10-10); never add another automatic trigger without the user's request.
- The only simulator variables the app writes (SimConnect, `src/SimLink.cs`) are `L:AUDIOINHIBIT`, kept at 1 while the option "Auto set default audio inhibit L:AUDIOINHIBIT" is ticked (on by default, the user's request of 2026-10-10), and the three status variables `L:HMC_VOICE_STATUS`, `L:HMC_VOICEPACK_VERSION`, `L:HMC_APP_VERSION`; never write other variables, and keep `SimConnect.dll` out of the repository (it is copied from the MSFS SDK at build time).
- Voice packs (`voicepacks/*.xml`): every change of the texts of a pack raises its `version`; the document `docs/architecture/VOICEPACKS.md` and `docs/DEVELOPER_GUIDE.md` (compiled into the program) describe the tags and the format and change in the same commit as the code; pack files are content, not user data, so they are tracked. `tools/check.js` validates them.
- The base pack `EN` is the reference of every translation (user request of 2026-10-11). The block between `MISSION TEXTS BEGIN` and `MISSION TEXTS END` in `voicepacks/EN.xml` (the checklist rows and dispatch descriptions the mission speaks as `<text:KEY>English`) is generated by `node tools/sync-pack-texts.js` from `tools/voice-texts.json` of the mission repository: never edit it by hand. When the mission gains or changes a spoken text (a new mission, a new checklist, a changed description), the mission side runs `node tools/voice-texts.js assign` and `sync`, and this side runs `node tools/sync-pack-texts.js` (the pack version goes up) in the same delivery; `tools/check.js` and the mission's `voice-texts.js check` fail when the two are out of step. A new key in the base pack turns the packs of the users that lack it red in the Voice packs tab, so say so in the changelog. A key is never renamed or reused for another text. The pack reaches the players apart from the program: after a change of `voicepacks/EN.xml` (pack version up) upload it to the release with the tag `voicepack-EN` (`gh release create voicepack-EN voicepacks/EN.xml --title "Voice pack EN" --notes-file <what changed>` the first time, then `gh release upload voicepack-EN voicepacks/EN.xml --clobber` and edit the notes), only when the user asks for a publication; the Updates tab installs it when its version is newer than the installed one and its `minapp` allows. Bump the `<pack:EN:n>` of `voice app connect` in the mission only when the mission needs a key through `<say:KEY>` (a `<text:KEY>` always has its English as the fallback).
- Network, process and file code must not leave processes behind: `piper.exe` children are stopped on exit.

## Build, release, and publication gates

1. Build or generate an artifact only after explicit authorization in the current request. Every authorized release advances the version exactly once (0.1, 0.2, 0.3, ...); `AppInfo.Version` in `src/Core.cs`, the two assembly attributes in `src/Program.cs`, the top entry of `CHANGELOG.en.md`, the "Version" line of `README.md` and `tools/release-ledger.json` must agree (`tools/check.js` enforces the first four against the sources and that the ledger is not ahead). `tools/release-ledger.json` is authoritative for the last delivered artifact; if it disagrees with the changelog or the task history, stop and ask instead of inferring.
2. After an authorized build run `node tools/check.js`, the self-tests of the executable that apply (`--selftest`, `--scan-work`, `--clean-work` on dummy data, `--run-index` on a temporary Community folder), `git diff --check`, status and diff review.
3. A delivered artifact is always named `HPGMissionCompanion.exe`; the installer built by the same `tools/build.cmd` from `setup/Setup.cs` is named `HPGMissionCompanionSetup.exe` and is published only as an asset of a GitHub release, never tracked (binary). Test the installer on a dummy folder (`/S /dir=...` then `/uninstall /S`), never over the runtime folder of the user. Static PASS never proves simulator behaviour: runtime status stays pending until tested in the simulator; runtime tests are standalone HPG test missions in `tests/` (and are also handed to the user in `Desktop\claude\tests`), never part of the production mission.
4. Publication is local by default (commit only). Pushing to GitHub requires explicit authorization for that specific push; `main` is the only branch, so a push is directly live. Never push opportunistically.
5. Release completeness is blocking: audit every carried requirement against source, tests, changelog and runtime evidence. Omitted, partial or unverified work blocks delivery; defer only with explicit user consent.

## Documentation

- Durable architecture belongs in `docs/architecture/`; runtime checks in `docs/testing/`.
- Update `CHANGELOG.en.md` only for an externally visible release (one entry per version, newest first).
- Document the current contract, ownership boundary or test procedure; do not write conversational handoffs. Do not claim static checks prove runtime behaviour.
